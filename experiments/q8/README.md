# 8 位编码与安全下界：精确查询原型

日期：2026-11-12。状态：仅保留在本地实验分支，不推荐整体替换当前版本。

## 结论

1 万行负载没有明显收益；10 万行的连续查询出现收益，但编码构建拖慢首查，且增加内存。不能把筛除比例、内核收益或预热后收益直接当成官方得分提升。

| 负载与口径 | 当前版本 | 最终原型 | 耗时变化 |
| --- | ---: | ---: | ---: |
| 1 万行、128 维、3,000 次随机查询，包含首查 | 2.139518 s | 2.143019 s | 慢 0.16%，基本持平 |
| 同上，扣除首查后的 2,999 次 | 2.135879 s | 2.135906 s | 基本相同 |
| 10 万行、128 维、128 次不同随机查询，包含首查 | 239.421 ms | 235.841 ms | 降低 1.50% |
| 同上，扣除首查后的 127 次 | 204.358 ms | 162.194 ms | 降低 20.63% |
| 10 万行重复查询，预热后每次延迟 | 1.758527 ms | 1.163192 ms | 降低 33.85% |

两种规模的随机查询均一半无过滤、一半带普通列等值过滤，K=10。每版本六轮，按 A/B/B/A、B/A/A/B、A/B/B/A 交替执行，各取中位数。10 万行不同查询的三个对照块，扣除首查后的平均耗时分别降低 20.45%、19.56%、22.58%。这支持当前本地大数据量下的持续查询收益，不代表所有数据分布均有收益。

代价：10 万行随机数据首查中位数 33.254 → 71.902 ms；整轮容器内存峰值中位数 118.98 → 131.59 MiB。1 万行首查 3.529 → 7.161 ms，内存峰值 14.74 → 15.64 MiB。额外 8 位码与原始 float32 同时保留，因此向量缓存的主体增大约 25%，并非整个数据库内存缩小四倍。

重复查询补充测试使用 1,024 个随机原型构成 100,000 行，最后一维区别主键；查询为同一个全零向量。它不能代替不同随机查询测试。该测试首查 28.893 → 73.308 ms，内存峰值 61.98 → 74.79 MiB。所有首查均从进程 ready 后计时；没有清空宿主页缓存，不能称为物理冷盘测试。

## 实现与安全条件

实现位于 `minivector-cpp/src/quantized_scan.h`，接入 `HotSet` 的精确升序 TopK 扫描。当前版本已经用 float32 直接差平方和筛选，再以补偿 double 距离维护堆；本原型在这两步之前增加编码筛选，不替换最终距离。

1. 选取二次幂步长 `s`，把数据四舍五入为 `[-127,127]` 的有符号 8 位码。零点为 0，不做可能引入大数相消的中心平移。每维量化误差最多 `s/2`。
2. 查询同样编码；超出编码区间时整条查询回退原有精确路径，不截断查询坐标。
3. 整数直接差平方和 `S=sum((code(x)-code(q))^2)` 精确累加。维度只支持 1..4096，故 `S <= 4096*254^2 = 264257536 < 2^31`。AVX2 与标量计算结果逐项一致。
4. 三角不等式给出 `d(x,q)/s >= sqrt(S)-sqrt(dim)`。当前堆满后，仅当 `S > (worst/s + sqrt(dim))^2` 的保守上界才排除记录。相等或不确定均继续走原有精确路径，候选数没有固定上限。
5. 实现为该阈值加入 `1e-9` 的乘法余量，覆盖 sqrt、加乘和堆中补偿距离的舍入误差。限定维度下 `32*epsilon(double)*(dim+8) < 3e-11`；余量大于此误差预算。输入是有限 float32、步长为二次幂，缩放可在 double 中精确表示；本范围的非零差平方不触及 double 下溢，最大距离也不触及 double 溢出。构建不启用 fast-math，不修改浮点环境。
6. 非有限输入、超出维度限制、编码预算不足、降序、事务覆盖层以及原本的磁盘回退路径继续使用原有算法。WHERE 仍在筛选前执行；距离并列仍按主键升序。

编码是可丢弃的内存缓存，没有新持久化文件；随整个 HotSet 在提交和恢复时失效、重建。空间计入现有缓存预算，无法分配则跳过编码加速。保留原来的事务、同步落盘和恢复逻辑。

## 诊断与验证

最终原型的单独诊断运行：编码检查 16,470,000 次，排除 16,116,339 次，即 97.85%。这是受检记录的比例；堆未满的记录不在分母内。诊断启用原子计数，不用于性能结论。

最初单累加器实现：1 万行查询 2.133122 → 2.159354 s，慢约 1.23%。改成四路整数累加器后得到上表结果。并没有观察到 1 万行明显提速。大数据量结果与减少原始向量访问的收益一致，但没有用硬件计数器证明缓存未命中或内存带宽就是唯一原因。

最终原型验证：

- 公开用例 20/20。
- 1 万行 A/B 查询合计 36,000 条、10 万行不同查询合计 1,536 条、重复查询合计 1,548 条，全部逐条核对主键、顺序与距离；独立 C++ 标量真值程序不引用数据库实现。
- 额外 4,800 条 Python float32 + math.fsum 真值检查，覆盖维度 2/31/128/129，大数相消、极大/极小值、并列、过滤、ASC/DESC、事务覆盖、修改和重启；缓存预算分别为 0/64 MiB。
- 150,001 行、48 项多线程及实际 SIGKILL 恢复检查。
- 响应上限、96 MiB 下事务溢写、跨表提交、提交前后强杀及恢复中再次强杀回归通过。
- 原始反例 `q=[100000000,0]`，1..100 为 `[100000000,1]`、101 为完全匹配：缓存 0/64 MiB 均返回 `[[101,0]]`。
- 独立 long double 下界测试共 2,969,064 次阈值判断、424,152 对向量，没有观察到错误排除；覆盖维度尾部、1..4096 维、指数 -149..120、匹配、并列、混合量级与量化边界。最终四路内核在 GCC13 ASan/UBSan 构建下运行通过。168 个查询超出编码范围并正确回退。

早期测试曾错误地断言所有随机查询必须能编码；数据范围较小时，该断言失败。修正测试以记录合法回退，没有放宽数据库结果检查。这里的 ASan/UBSan 是独立编码内核测试，不是本轮完整数据库的 sanitizer 运行。有限测试也不是对所有浮点输入的穷举证明。

## 条件、原始证据与复现

对照基线为当前工作版本 `28695d19460afa9ab2b501c31719b214427222d4`，包含首查缓存简化与 `-O3 -flto`；没有退回更慢的正式版本作基线。两引擎均由同一个 GCC 13.5.0 镜像、相同 Makefile/Dockerfile 编译。容器限额为 2 CPU / 2 GiB、禁用网络和 swap；独立容器、ext4 数据目录。性能运行与验证运行分开，没有同时跑验证占用 CPU。

`evidence/manifest.json` 包含 GCC 基础镜像 ID、源码 SHA256、对照基线和测试工具版本；各性能 JSON 中保存完整镜像 ID、输入真值哈希、逐轮时延、cgroup CPU、峰值内存和 I/O 快照。`derived-summary.json` 是从逐轮数据计算的衍生结果。独立真值程序使用宿主编译器，数据库本身均使用 GCC13。

计时包括进程协议、控制器 JSON 解码与等待。对照脚本没有统一预热，表中明确区分包含首查与扣除首查的口径。cgroup 查询阶段的物理 I/O 增量在这些内存负载中为 0；启动镜像读取和写回受页缓存影响，且快照在 shutdown 前采集，不能据此声称完整官方 B 指标改善。没有计算官方得分，也没有正式提测。

在 Ubuntu WSL 中从该工作树根目录执行：

```sh
docker build -t mvd-exact-candidate:q8-unrolled .
python3 experiments/q8/compare.py
python3 experiments/q8/large_compare.py
python3 experiments/q8/diverse_large_compare.py
python3 experiments/q8/validate.py
python3 experiments/q8/cancellation.py

```

性能脚本必须逐个运行。它们复用工作区相邻目录的 `contest-runtime/minivectordb-comparison-20261110` 和既有真值/协议工具，路径及版本见 manifest；并非脱离工作区即可运行的独立题包。基线镜像 `mvd-exact-candidate:continuous-lto` 可在上述基线提交的独立工作树按同一 Dockerfile 构建。将来重新构建应固定 manifest 中的 GCC 镜像 ID，不能假设浮动标签永远相同。
